# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** 예외는 "적용 기준" 섹션에 명시된 것만 유효하다. 그 외의 예외는 전부 변명이다.

## 0. 우선순위

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그 규칙이 이 파일보다 우선**한다. 충돌하는 내용이 없을 때만 이 파일을 적용한다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (계산, 상태 전이, 도메인 규칙)
- **API 엔드포인트 / 핸들러**
- **유틸리티 함수** (순수 함수, 변환기, 파서 등)
- **버그 수정** (재현 테스트 없이 수정 금지)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, build script)
- **순수 UI 마크업** (로직 없는 프레젠테이션 컴포넌트)
- **SQL / 마이그레이션 스크립트**

대상이 애매하면 "비즈니스 로직을 포함하는가?"로 판단한다. 포함하면 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 마라.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED가 아니라 버그다 — 고치고 다시 실행해 진짜 실패를 확인하라.

### GREEN

- **테스트를 통과시키는 최소한의 코드만 작성**한다. YAGNI — 지금 테스트가 요구하지 않는 기능은 추가하지 마라.
- 신규 테스트와 **기존 테스트 전부가 통과**하는 것을 확인한다. 일부만 확인하고 넘어가지 마라.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 전체 테스트가 **green을 유지**하는지 매 변경 후 확인한다.
- **새 동작을 추가하지 마라.** 리팩터링 중 "김에 하나 더" 떠오르면 다음 사이클의 RED로 미룬다.

### 반복

리팩터링이 끝나면 **다음 동작에 대한 RED로 돌아간다**. 사이클을 건너뛰지 마라.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 참고용으로 남겨두고 테스트를 나중에 맞추는" 방식은 **금지**한다. 주석 처리, 별도 브랜치 보관 등 어떤 형태의 보존도 허용하지 않는다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용이 낮다. 단순함은 생략의 이유가 아니라 작성이 쉬운 이유다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 그 순간부터 회귀 위험을 안고 누적된다. |
| "시간이 없다" | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 항상 더 든다. 지금 아끼는 시간은 나중에 이자와 함께 갚는다. |
| "삭제하면 낭비" | 검증되지 않은 코드는 자산이 아니라 부채다. 낭비는 삭제가 아니라 잘못된 코드를 유지보수하는 것이다. |
| "프로토타입이다" | 프로토타입은 살아남아 프로덕션이 된다. 지금 대상이 "적용 기준"에 해당하면 예외는 없다. |
